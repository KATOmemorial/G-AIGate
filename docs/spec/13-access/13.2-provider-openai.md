## 1. 模块定位

共享内核 `internal/provider` 的字段级冻结 + OpenAI 适配器（真实上游的 HTTP 客户端）。所有上游流量（真实厂商与 mock）都经它进出。

## 2. 目标 / 非目标

**目标**：`ChatRequest / ChatResponse / StreamEvent / Stream` 字段冻结；OpenAI 适配器（`Chat` / `ChatStream`）；SSE 解析器；上游错误分类（携带状态码，供 16.4 判定可重试性）。

**非目标**：候选选择与重试（16）；转发与背压（15——适配器只产出事件流）；非 OpenAI 厂商适配器（接口已隔离，加一个 adapter 即接入，这是验收 12 之外的扩展点）。

## 3. 输入输出

```go
// internal/provider —— 字段级冻结
type Message struct{ Role, Content string }

type ChatRequest struct {
    Model    string
    Stream   bool
    Messages []Message            // 17.1 估算回退用
    Extra    map[string]json.RawMessage // 其余字段原样透传（见决策①）
}

type ChatResponse struct {
    Body  json.RawMessage         // 上游响应原样（含 usage），网关不重排
    Usage *Usage
}

type Usage struct{ InputTokens, OutputTokens int64 }

type StreamEventKind uint8 // Chunk | UsageDone | Error
type StreamEvent struct {
    Kind  StreamEventKind
    Raw   []byte   // 原始 data 负载（不含 "data: " 前缀）
    Usage *Usage   // 仅 UsageDone
}

type Stream interface {
    Events() <-chan StreamEvent
    Close() error  // 取消上游 HTTP 请求、关闭 body、收敛 goroutine
}

// 适配器（OpenAI 兼容）
func NewOpenAI(httpClient *http.Client) Provider  // 实现 00 §6.1 的 Provider 接口
```

**SSE 解析规则**（与 12.1 帧格式互为验收对象）：`data: [DONE]` → 流结束（不发事件）；`data: {...}` 且 JSON 含非空 `usage` → `UsageDone`；其余 → `Chunk`；`event:`/注释行/心跳按 OpenAI 实践忽略。**适配器内部读取 goroutine → 有界 channel（容量 = ProxyConfig.StreamBuffer）**——15.2 的背压链条第一环在这里。

**错误分类**（16.4 的切换依据）：

```go
type UpstreamError struct {
    StatusCode int      // HTTP 状态码；0 = 网络/连接层错误
    Body       []byte   // 上游错误响应体（截断至 1KB）
    Retryable  bool     // 429 / 5xx / 网络层 = true；400/401/403/404 = false
}
```

## 4. 设计说明

1. **最小理解 + 原样透传**：网关只"理解"路由与计量必需的字段（model/stream/messages），其余进 `Extra` 原样转发。理由：OpenAI 生态字段（tools、function_call、response_format...）持续演进，typed struct 白名单必然滞后，会静默丢字段破坏兼容——这是网关类产品最常见的坑，面试可讲。
2. **强制注入 `stream_options.include_usage`**（仅 stream=true）：构造上游请求时重写该字段，保证 17.1 有真 usage；副作用是客户端可能收到未请求的 usage 帧——主流 SDK 忽略末尾未知帧，保真优先，文档化。
3. **模型名重写发生在适配器**：`req.Model` 按端点配置改写为 `ep.Model`（上游名），对内对外名字分离（11.1 `upstream_model` 列的兑现点）。

## 5. 验收标准（可执行）

```bash
go test ./internal/provider/...    # httptest 模拟上游，用例：
# ① 序列化：带 Extra 的请求转发后未知字段不丢失（深比较 JSON）
# ② stream=true 时上游请求体含 stream_options.include_usage=true；stream=false 不注入
# ③ 模型名重写：ep.Model="gpt-4o-real" → 上游收到 gpt-4o-real
# ④ SSE 解析：Chunk/UsageDone 分类正确；[DONE] 结束； UsageDone 携带 usage
# ⑤ 错误分类：429 → Retryable=true；400 → false；连接拒绝 → StatusCode=0,Retryable=true
# ⑥ ChatStream 返回的 Stream：Close() 后 Events 不再投递、httptest 上游收到 ctx 取消
# ⑦ 事件 channel 容量 = StreamBuffer（慢消费时读取 goroutine 阻塞而非丢弃）

# 与 12.1 的交叉验收（真 mock）：

go test ./internal/provider/... -tags mock_e2e   # 五场景经适配器各跑一遍
```

## 7. 主要风险

- 上游 SSE 的非标准行为（多行 data、CRLF）——解析器按行分割后 trim `\r\n`，用例覆盖 CRLF。
- `ChatStream` 返回时机 = 收到响应头；首事件等待（TTFB 语义）由 15.2 计时——两模块的时间边界在本 PR 文档写清，避免双计时。
