# 13.4 用户 Key 管理 API（L2）

> 状态：草案（待 review） | 上游：[13-L1](../13-access.md) | 批次：B3 | 预计工作量：0.5 天
> 上下文包：[00-总纲](../00-总纲.md) §7（API 设计 §7 of 设计文档）、13.1（GenerateKey / APIKeyRepo）、19-L1 §3（页面数据源）

## 1. 模块定位

终端用户对 Key 的自服务：创建（明文仅返回一次）、列表（只见前缀）、吊销。19.1 用户控制台的直接后端。

## 2. 目标 / 非目标

**目标**：`/api/v1/user/keys` 的 GET/POST/DELETE；`UserAuth` 中间件缝（B3 桩、19.1 替换为会话）。

**非目标**：配额与用量查询（17 的 API）；管理员管理他人 Key（19.2）；Key 轮换（后续扩展）。

## 3. 输入输出

```
POST /api/v1/user/keys        {"name":"我的应用"}（可选，默认 ""）
→ 201 {"id":7,"name":"我的应用","key":"sk-AbCdEfGh...","key_prefix":"sk-AbCdEf",
       "created_at":"..."}     ← 明文唯一一次出现；响应头 Cache-Control: no-store

GET /api/v1/user/keys
→ 200 [{"id":7,"name":"我的应用","key_prefix":"sk-AbCdEf","status":1,"created_at":"...",
        "expired_at":null}, ...]   ← 永不含明文/hash

DELETE /api/v1/user/keys/:id  → 204（幂等：已吊销再删仍 204）
                                → 404（非本人的 Key，不泄露存在性）

// 鉴权缝（消费方接口，同 13.3 模式）：
type UserAuth interface { Identity(ctx) (*Principal, error) }  // B3: 桩（允许指定用户，TODO(19.1) 会话替换）
```

**实现要点**：POST = `GenerateKey()` → `APIKeyRepo.Create`（prefix/hash 入库）→ 返回明文；吊销 = `Revoke`（status→0），13.1 的鉴权路径立即拒绝（无缓存，13.1 决策③在此兑现为优点）。

## 4. 设计说明

1. **明文只出现一次**是密码学存储的完整闭环：生成（13.1）→ 存储（hash）→ 展示（一次）→ 遗失只能重建。整套是面试"API Key 系统怎么设计"的完整体。
2. **DELETE 语义用 204 幂等**：吊销是状态收敛操作，重复调用不是错误；但**他人 Key 返回 404 而非 403**——不泄露存在性。
3. UserAuth 缝与 13.3 的 Prechecker 缝同模式：B3 期间可脚本自测，B7 接会话零改业务代码。

## 5. 验收标准（可执行）

```bash
go test ./internal/access/... -run TestUserKeys   # 用例：
# ① POST → 201，明文符合 sk- 前缀与长度；DB 中只有 prefix+hash
# ② 同一明文再查库不存在（GET 响应与 DB 均无明文）
# ③ GET 列表字段白名单（响应不含 key_hash 字段）
# ④ DELETE 后：DELETE 重复 → 204；用旧 Key 调 /v1/chat/completions → 403（闭环）
# ⑤ 用户 A 操作用户 B 的 Key → 404
# ⑥ 响应头含 Cache-Control: no-store
```
