## 1. 模块定位

可编程上游的"服务端"：`cmd/mockprovider` 进程，一个 OpenAI 兼容的 `/v1/chat/completions` 端点，按渠道（上游 Key）当前场景生成对应行为。B3~B6 全部验收脚本的上游地基。

## 2. 目标 / 非目标

**目标**：场景引擎（per-Key 状态 + 请求头覆盖 + 立即生效）；五种场景的流式与非流式实现；SSE 帧格式与 OpenAI 一致（含 usage 末帧）。

**非目标**：控制 API 与验收脚本（12.2）；真实推理（模板文本）；`/v1/models` 之外的兼容面。

## 3. 输入输出

```go
// internal/mock（独立包，仅 Gin 依赖，不 import 任何 internal/* —— 00 §5.2）
type Scenario string
const (
    Normal       Scenario = "normal"
    Slow         Scenario = "slow"
    Downtime     Scenario = "downtime"
    RateLimited  Scenario = "rate_limited"
    Interrupted  Scenario = "interrupted"
)
type ScenarioParams struct { // 全部有默认值，本 L2 冻结
    Chunks          int           // normal: 8
    ChunkInterval   time.Duration // 50ms
    TTFBDelay       time.Duration // slow: 2s
    DowntimeMode    string        // "503" | "refuse"，默认 "503"
    FailAfterChunks int           // interrupted: 3
    PromptTokens    int           // 12（生成的 usage）
    CompletionTokens int          // 34
}
type Engine interface {
    Set(key string, s Scenario, p ScenarioParams)  // 立即生效（RWMutex）
    Get(key string) (Scenario, ScenarioParams)
    Resolve(key, overrideHeader string) (Scenario, ScenarioParams) // header > per-key > 全局默认 normal
}
```

**SSE 帧格式**（与 OpenAI chunk 一致，13.2 的解析器以它为验收对象）：

```
data: {"id":"chatcmpl-mock","object":"chat.completion.chunk","created":0,"model":"gpt-4o-demo","choices":[{"index":0,"delta":{"content":"..."}}]}

...（Chunks 帧）...
data: {"id":"chatcmpl-mock","object":"chat.completion.chunk","choices":[{"index":0,"delta":{}}],"usage":{"prompt_tokens":12,"completion_tokens":34,"total_tokens":46}}

data: [DONE]

```

usage 帧仅在请求带 `stream_options.include_usage` 时输出（与 OpenAI 行为一致，验证 13.2 的注入是否生效）。**非流式**（`stream:false`）：单次 JSON 响应，含 `usage`。

**各场景行为实现**：`normal` 按 Chunks/ChunkInterval 发帧后收尾；`slow` 先 sleep TTFBDelay 再走 normal；`downtime` 按 DowntimeMode 返回 503 或直接关闭 listener 侧连接（`refuse` 模式实现为立即 `conn.Close()`）；`rate_limited` 返回 429 + `Retry-After: 1`；`interrupted` 发 FailAfterChunks 帧后 **flush 并关闭连接**（不输出 usage 帧与 [DONE]）。

**配置**：`MOCK_ADDR`（默认 `:18080`）。

## 4. 设计说明

1. **响应分块与 Flusher**：每帧 `write + flush`，保证 `interrupted` 的断流时机真实（客户端确实收到 k 帧后连接断开）——这是 15/16 验收"流式中断计失败"的信号源。
2. **usage 帧的条件输出**：故意与 OpenAI 语义对齐，让"13.2 强制注入 include_usage → 17.1 拿到真 usage"这条链路在 B3 即可端到端验证。
3. **DowntimeMode 双模式**：503（HTTP 层故障，网关可识别错误码）与 refuse（TCP 层故障，触发网关连接错误路径）——两类故障在熔断统计里都要正确计为失败。

## 5. 验收标准（可执行）

```bash
go test ./internal/mock/...   # httptest 驱动，用例：
# ① normal：帧数 == Chunks，含 [DONE]，include_usage 时末帧带 usage；不含时无 usage 帧
# ② slow：TTFB ≥ TTFBDelay
# ③ downtime/503：状态码 503；downtime/refuse：客户端收到连接重置
# ④ rate_limited：429 + Retry-After
# ⑤ interrupted：收到 FailAfterChunks 帧后连接关闭，无 [DONE]
# ⑥ 非流式 normal：单 JSON 响应含 usage
# ⑦ header 覆盖优先级：X-Mock-Scenario > per-key > 默认

# 进程级冒烟：
go run ./cmd/mockprovider &
curl -s -H "Authorization: Bearer sk-mock-a" -H "X-Mock-Scenario: interrupted" \
     -d '{"model":"gpt-4o-demo","messages":[{"role":"user","content":"hi"}],"stream":true}' \
     localhost:18080/v1/chat/completions   # → 若干帧后连接断开
```

## 6. 依赖

## 7. 主要风险

- `refuse` 模式的实现方式（hijack 后关连接 vs 拒绝前的延迟）要贴近真实 TCP 故障——用 curl 实测验证错误类型为连接重置/EOF。
- Windows 宿主机防火墙对 18080 的拦截——冒烟命令即验证。

实现机制：状态锁只保护 map 复制／替换；所有等待与网络写出均在锁外。SSE 对每帧 Write＋底层 FlushError 检查，绕过 Gin 无错误返回的 Flush；内容、usage、DONE 写入／Flush／短写失败分别有停止后续生产的断言。真实中断使用 `http.ErrAbortHandler`，装配 `gin.New()`，日志中间件只 defer 摘要、不 recover 故障注入。

日志不记录 Key、Authorization 或请求正文，也未输出 Key 前缀；合法 `req_`＋ULID 可沿用，其余重新生成。`chunks_written` 为成功 Write＋Flush 的内容帧计数，usage／DONE 不计入，非流式为 0。未通过校验／未解析场景的日志仍保留字段，但 model／scenario 可为空。Shutdown 用独立 3s 预算，超时后 Close、取消请求基上下文、通过受互斥 gate 保护的 WaitGroup 确认 handler 退出。
