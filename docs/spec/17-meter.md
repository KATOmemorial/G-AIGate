## 1. 模块边界

**做什么**：Token 计量（流式逐分片累计、非流式、估算回退）；配额预检与结算（分层配额）；计价（`model_prices` → 微元成本）；账单聚合与查询；用户额度/用量查询 API。

**不做什么**：渠道选择与重试（16）；Key 管理（13）。配额**配置**的 CRUD 页面在 19，但配额**语义**（预检/结算/层级）全部在本模块。

## 2. 接口

- 跨模块契约：00 §6.6（`QuotaGuard` / `UsageSink`）。
- HTTP：`GET /api/v1/user/quota`（额度与已用）、`GET /api/v1/user/usage`（我的用量统计）、`GET /api/v1/billing/summary`（+ CSV 导出，财务页数据源）。
- 用量优先级：上游 usage（末 chunk / 非流式响应）> 本地估算（字符数 / 4，落库标记 `estimated=true`）。
- 配额模型：`target_type ∈ {api_key, user, group}`，`period ∈ {daily, monthly}`；一次请求预检**依次检查三层**（key → user → group），任一硬超限即拒；结算时向三层计数器分别累加。

## 3. 关键设计决策

1. **竞态方案：事后结算 + 弹性容忍**（本模块第一面试题，标准答法）。预检只读不锁不预扣；预检与结算之间的并发窗口内可能少量超限——对内部网关可接受，且硬超限在 `Settle` 后由计数器拦截后续请求。**为什么不用预扣**：预扣需要完整的回补路径（流中断、整体超时、网关崩溃三种异常都要回补，否则比超限更糟——漏记/双扣），状态机复杂度远超收益。两种方案的 trade-off 都要能讲。
2. **计价全程整数**：`cost = ceil(tokens × price_per_m / 1e6)`，微元 int64（00 §7.4），杜绝浮点累计误差；价格按 `model` 查 `model_prices`（`effective_from` 生效版本）。
3. **账单单一数据源**：`bills` 是 `usage_records` 的定时物化聚合（月表），对账永远以明细表求和为准——"账单 = 明细之和"是 B6 验收断言。

## 4. L2 清单（与 00 §4.1 预排一致，无调整）

- **17.1 Token 计量**：分片累计、usage 提取（13.2 注入的 `include_usage`）、估算回退与 `estimated` 标记。
- **17.2 配额预检与结算**：三层检查、Redis 计数（00 §7.2 key）、软阈值告警点、**并发正确性测试（`-race`）**。
- **17.3 计价与账单**：价格查询、整数计价、月账单物化任务、查询/导出 API。

## 5. 主要风险

- 估算误差（±20% 量级）：仅在上游不回报 usage 时触发，落库标记可见，账单页注明。
- 三层配额 × 两种 period 的组合数：预检路径须短路（最严层先判），避免每请求 6 次 Redis 往返——用一次 MGET/HGETALL 批量读。
- Redis 计数与 MySQL 配额配置的一致性：配置变更低频，走 11 的缓存 TTL 收敛。

## 6. 验收要点

B6 检查点（全模块）：并发 100 请求打在配额边界——拒单数 ≥ 1、无漏账（成功请求全部落明细）、无双扣（明细求和 = Redis 计数增量）；软阈值触发告警点；账单聚合值 = 明细求和。脚本入库 `test/e2e/quota_race.sh`。
