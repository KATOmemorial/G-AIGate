## 1. 本文档的作用与冲突处理

- 设计文档是"为什么"层，本文档是"执行事实"层。两者冲突时：**执行以 00 为准**；如冲突暴露了设计缺陷，先在 §11 变更记录中修正 00，再动代码。
- 本文档的直接受众是**每一份 L2 施工文档背后的独立 vibecoding 会话**。因此所有跨模块共享的事实（接口签名、表结构、Redis key、编号、批次）必须且只能在这里唯一定义。
- 契约（§6、§7）的修改权限在"00 变更流程"（§10），任何 L2 会话无权自行变更契约。

### 2.2 L2 文档模板（九段，每份 L2 必须完整包含）

1. **模块定位**：一段话 + 在全局管道（§3.1）中的位置
2. **目标 / 非目标**：本会话做什么、明确不做什么（防止会话自由发挥）
3. **输入输出**：对外接口签名、依赖的接口节选、涉及的数据表 / Redis key
4. **设计说明**：关键决策 2~3 条及理由（面试素材的直接来源）
5. **验收标准**：可执行——测试用例清单 + 场景脚本（命令 + 期望输出）
6. **依赖**：上游文档编号、谁依赖我
7. **主要风险**：已识别的坑与预先取舍
8. **预计工作量**：实现 + 测试粗估
9. **上下文包**：引用 00/01 的哪些小节 + 依赖接口的签名节选（保证单会话自包含）

以上九段为撰写模板；实现会话完成后、合并回 main 前，须**追加"验收记录"章节**（编号顺延，先例见 10.1 §9）：交付清单（分支与 commits）、验收命令输出全套、实现记录（与文档的对应关系、偏差及理由、实现反馈触发的文档修正）。无验收记录的 L2 不得合并。

## 3. 系统概览

### 3.1 数据面管道（一条请求的生命周期）

```
客户端
  │ POST /v1/chat/completions   (Authorization: Bearer sk-...)
  ▼
[10 骨架]      RequestID 注入 → 访问日志 → recover
  ▼
[13 access]    ① 鉴权：Key → Principal（用户/Key/分组）
  ▼
[17 meter]     ② 配额预检：硬阈值拒单，软阈值打告警点
  ▼
[16 router]    ③ 路由：模型(别名)→候选渠道链（过滤禁用/熔断）
               ④ 容灾执行：逐个尝试，首字节失败 → 下一候选
  ▼
[15 proxy]     ⑤ 流式转发：背压/取消传播/双超时，逐分片累计 token
  ▼
[17 meter]     ⑥ 结算：用量落账（usage_records）+ 配额计数
  ▼
[18 metrics]   全程打点：延迟/错误/成本，按渠道/模型/用户维度
```

横切支撑：`[11 store]` MySQL 冷数据 + Redis 热状态；`[12 mock]` 可编程上游；`[14 channel]` 渠道健康与端点选择；`[19 web]` 管理与用户页面；`[20 deploy]` 部署与观测面板。

### 3.2 全局时序约束（三句话，凌驾于所有 L2 之上）

1. **容灾只发生在首字节之前**。响应头一旦写给客户端，该请求不可再切换上游；流式中断视为该渠道一次失败，计入健康与熔断统计。
2. **配额是两阶段语义**：预检放行 → 消费后结算。预检不阻塞请求路径；竞态的具体机制（弹性阈值 / 预扣回补 / 事后核销）由 17.2 冻结，但语义不可变。
3. **一个 RequestID 贯穿始终**：日志、指标、账单三者必须能凭同一 RequestID 对账。

## 5. 依赖规则

### 5.1 分层（依赖只能自上而下）

```
第 0 层 基座       11 store、12 mock-provider、共享内核 internal/provider
第 1 层 数据面     13 access、14 channel、15 proxy、16 router、17 meter
第 2 层 观测视图   18 metrics（横切，被第 1 层依赖）、19 web
第 3 层 部署       20 deploy
装配层            10 骨架（依赖全部，组装；无人依赖它）
```

禁止：反向依赖、跨层环、同层模块间非契约依赖。

### 5.2 依赖边（模块级）

```
internal/provider（共享内核：接口 + 统一请求/响应类型，不 import 任何业务包）
    ▲ 实现：13 的 openai 适配器
12 mock-provider → 独立 HTTP 上游，不实现 Provider；internal/mock 不依赖其他 internal 包，cmd 仅装配自身模块；13 的适配器经 HTTP 调用
13 access   → 11 store（用户/Key 读取）、内核
internal/provider/openai → internal/provider（13.2 的适配器子包；标准库 HTTP，不 import access）
14 channel  → 11 store（渠道/Key 表）、内核（产出 provider.Endpoint）
16 router   → 14 channel（健康判定 IsAvailable、端点选择 EndpointPicker）
             11 store（别名/渠道列表）、15 proxy（执行器调用转发）、17 meter（结算）
15 proxy    → 内核（消费 Provider 流）
17 meter    → 11 store（配额/账单表）
18 metrics  → 无业务依赖（被 13~17 打点调用）
19 web      → 13（Key 服务／身份接缝）、14/17 暴露的管理与读取 API、11 store
20 deploy   → 全部（打包与编排）
```

关键说明：

- **健康与熔断是两套独立判定**，同一请求结果分别喂给两者：`14.3 健康状态机`（连续失败/探活信号 → 渠道禁用/恢复，带冷却防抖）与 `16.3 熔断器`（滑动窗口错误率 → 三态开关）。窗口、语义、恢复条件各自独立冻结，不许合并。
- `internal/provider` 是唯一允许被多模块 import 的"类型包"，只放接口与数据类型，禁止逻辑。
- B3 的临时编排和渠道读取放在 `internal/bootstrap`，只由 cmd 装配层调用；它可依赖 access／store／secret／provider／proxy，业务模块不得反向 import bootstrap。access 只消费自身定义的入口接口，不 import router／meter／proxy／bootstrap；B5／B6 在装配处换入正式实现，避免 router 依赖 access 后形成环。
- `internal/middleware` 是既有横切设施，13／16 及装配层可调用其 context／日志辅助；middleware 不反向依赖业务包。13.3 的冻结增量在 AccessLog 入口建立请求内共享摘要，既有 WithUserID／WithModel／WithChannelID 保持签名并同步摘要，使内层派生 context 的字段在外层完成日志中可见；摘要必须请求隔离且并发安全，不存身份凭据或正文。Principal 仍为标准 context 中的身份值，不拿日志摘要授权。

## 6. 接口契约总表（权威，已冻结）

> 签名为 Go。实现包名见 §5.2。此处只冻结**跨模块**契约；模块内部接口由各 L1 冻结。字段级细节（struct 完整字段）在标注的 L2 冻结，此处冻结方法签名与语义。

### 6.1 共享内核 `internal/provider`（13.2 冻结字段）

```go
// Endpoint：一次上游调用的目标，由 14-channel 产出（渠道 + 轮询选出的 Key + 模型名映射）
type Endpoint struct {
    ChannelID int64
    Provider  string // "openai" | "mock" | ...
    BaseURL   string
    APIKey    string // 已解密
    Model     string // 映射后的上游模型名
}

type Usage struct{ InputTokens, OutputTokens int64 }

type ChatRequest struct{ /* OpenAI chat 请求的内部子集，字段清单 13.2 冻结 */ }
type ChatResponse struct{ /* 同上 */ }

type StreamEventKind uint8 // Chunk | UsageDone | Done | Error；符号名见 13.2

type StreamEvent struct {
    Kind  StreamEventKind
    Raw   []byte // 原始 SSE data
    Usage *Usage // 仅 UsageDone 携带
    Err   error  // 仅 Error 携带，必须非 nil；不序列化给客户端
}

type Stream interface {
    Events() <-chan StreamEvent
    Close() error // 幂等：取消上游、关闭 body、等待所属 worker 退出
}

type Provider interface {
    Name() string
    // 非流式。返回响应与用量。
    Chat(ctx context.Context, ep *Endpoint, req *ChatRequest) (*ChatResponse, *Usage, error)
    // 流式。内部错误经由 Error 事件传递；网络层错误由返回值传递。
    ChatStream(ctx context.Context, ep *Endpoint, req *ChatRequest) (Stream, error)
}
```

冻结补充：`Done` 独立表示上游 `[DONE]`，必须向下游转发一次；关闭事件 channel 本身不代表成功。未见 Done 的 EOF／非法帧／读失败均为异常；取消由请求 context 分类，不伪造 Done。Raw 保留 SSE data 负载的内容，非整段 HTTP 字节；组帧规则见 13.2／15.1。`Error.Err` 保留可分类原因。正常流可以缺 usage，不能缺 Done。

### 6.2 access（13）

### 6.5 router（16）

本节为既有冻结基线；未实现部分的B5替代候选见§6.11，候选批准前不覆盖本节效力。

```go
type Plan struct {
    Model      string
    Candidates []*provider.Endpoint // 有序：主渠道 → 回退链；已滤除禁用/熔断渠道
}

type Router interface {
    // 解析模型与策略产出有序候选；全部不可用返回 ErrNoCandidate
```

### 6.9 B3 转发与装配补充契约（v0.9 已冻结）

规划只读HealthRegistry.IsAvailable与Breaker.Inspect；不Acquire、不选Key、不解密、不调用Provider。Inspect对冷却已到或过期probe可返回Eligible=true，不占half-open许可。明确返回的error终止规划；bool健康故障仍按14.3排除。64上限针对过滤前的去重候选，超限报配置错误、不静默截断；default／fallback ID须为正且可表示int64。配置仍有既有60s跨副本缓存窗口，不承诺规划与执行间分布式快照。

Auto的优先级为别名非空strategy→全局router.default-strategy；显式合法strategy只供内部调用覆盖，HTTP body／header不开放路由选择。weighted在同priority组内生成按正权重的不放回随机排列，首位概率按权重；不是渠道Key的SWRR。cost_first按候选UpstreamModel查PriceRepo当前生效CNY单价，比较input_per_m+output_per_m的精确整数和，表示等量输入／输出的排序代理、不是实际计费；缺价格排在已知价格后，同值按ID，数据库错误不降级。不同渠道映射到同一模型时同价，不虚构渠道折扣或新增价格列。

latency_first不读MySQL展示列。16.2自持每实例、按(channelID, 对外别名)的成功完整attempt耗时样本：60s滑动时间窗、每键最近256个、最近至少5个才有p99，nearest-rank ceil(0.99*n)；同priority内已知p99升序，冷样本排后，同值／全冷按ID。最多4096个键，淘汰最久未观察键并以ID／别名稳定打破同值，无自建定时worker。只由16.4在ResultSuccess时喂实际完整attempt耗时；不使用FirstByteMs、失败、重试间隔或probe代替p99。该统计为本实例近期样本，不承诺跨副本全量P99；展示列生产及18.1指标仍后置#32。

**3. 熔断许可与时间**：16.3独占Lua及Redis业务状态，状态时钟使用Redis TIME毫秒，逻辑窗口为(now-window, now]。Inspect只读且不初始化／转移／清理。Acquire在尝试时原子检查并发名额；closed也发permit以支持去重／晚到隔离；open到期才允许一个half-open持有者，多副本不能各占一个。Complete消费一次有效permit，success／failure记样本，中性不记；重复、过期或旧epoch结果不改变当前窗口／状态。half-open成功清窗并closed，失败重开冷却，中性释放资格但不宣称恢复；持有者消失由lease到期恢复领取资格。所有已取得permit都须至多完成一次，未发起上游亦须neutral释放。

沿原参数默认window=60s、min-samples=20、err-threshold=0.5、open-duration=30s。新router.state-timeout=500ms、route-timeout=2s、max-attempts=3。router时长均正整毫秒：window／open-duration至多1h，state／route至多1min；min-samples为1..1000000；threshold须有限且能表示为1..1000000的整数百万分比，比较使用整数口径；max-attempts为1..16。新字段及既有细化校验、默认、env、样例由16.1／16.3／16.4各自交付，不回写10.1历史。lease由逻辑请求剩余预算＋一次反馈预算＋proxy既有500ms收敛容差向上到毫秒生成，上限24h；16.4构造校验proxy.overall-timeout加上述余量不超过上限，不借lease延长真实请求期限。

候选Redis key为`gaigate:breaker:{channelID}` HASH、`gaigate:breaker:events:{channelID}` ZSET、`gaigate:breaker:pending:{channelID}` ZSET，同一hash tag；原§7.2单行HASH+ZSET占位据此细化。状态HASH不TTL，窗口ZSET用TIME裁剪并设置至少window的TTL，pending逐项到期清理、key TTL不早于所有有效lease；绝不能因TTL先到而遗忘活跃half-open持有者。epoch为不透明唯一字符串，避免Lua uint64精度；事件member使用唯一permit token和结果标记，同毫秒不同请求不覆盖。每渠道最多4096个在途permit，满时拒绝新领取，不丢已有许可；窗口不截断有效样本。多副本必须采用相同策略指纹，既有HASH指纹不符／坏类型／Redis错误返回可分类error，fail closed，不自动清空状态。变更策略须协调停流并由运维显式清理该渠道这三类状态，B5不新增裸管理重置API。

**4. 执行／预算与回退**：16.4装配适配器实现access.ChatExecutor，进入时创建一个逻辑Overall预算（沿proxy.overall-timeout，继承更早父期限），先Route再Execute；Route另受route-timeout及同一剩余预算限制。每attempt仍由proxy在opener前启动原TTFB／Overall，父预算不刷新；最大真实opener次数max-attempts，候选每渠道至多一次，无固定sleep／Retry-After等待、后台重试或同渠道换Key重试。

尝试前重检健康→Acquire→Pick一次→校验Endpoint与计划渠道／映射一致→交proxy。无健康／无许可可跳过；无Key、mapping删除或映射已变则neutral释放并跳过，不在本请求重规划。SQL／解密等真实故障终止，不能报成上游失败。Plan不持明文Key；Endpoint只留在实际attempt局部，不打印／序列化；未尝试候选不调用picker。Pick及状态操作均有ctx上界，局部准备使用route-timeout／更早逻辑期限，不无限等待；已取得许可的所有退出路径都回收。

仅在WroteHeader=false、客户端及逻辑预算仍有效、还有未尝试候选且未达次数上限时，按下表考虑回退。提交状态与Kind分开；不因Cause含Canceled覆盖已裁定的OverallTimeout。

| 结果 | 可回退 | breaker结果 | 健康信号 |
|---|---|---|---|
| success | 否 | success | true |
| ttfb_timeout／overall_timeout | 是，须有剩余逻辑预算 | failure | false |
| stream_interrupted | 是，仅尚未提交 | failure | false |
| upstream_error，匹配UpstreamError且Retryable=true | 是 | failure | false |
| upstream_error，HTTP400／404／422 | 否 | neutral | 忽略 |
| 其他upstream_error（含401／403及协议错误） | 否 | failure | false |
| client_canceled／write_error | 否 | neutral | 忽略 |
| 未发起上游／准备失败 | 仅上述明确可跳过情形 | neutral | 忽略 |

反馈沿14.3同步有界清理方式保留request_id，breaker Complete和health Report共用一个不超过min(router.state-timeout, channel.state-timeout)的总清理ctx，不为每项重开。反馈失败安全记录，不覆盖已成功响应或触发回退；丢失half-open回报仍由lease恢复。不合并两个状态机；14.3后台probe只喂health，不释放breaker许可。

无任何Provider调用且候选耗尽返回ErrNoCandidate／503；已有尝试后耗尽返回最后一次实际失败／502或已冻结上游请求错误映射，不附加ErrNoCandidate篡改优先级。逻辑总预算耗尽返回ExecutionError.TimedOut=true；已提交后由原access路径异常终止，不拼接第二个响应。日志摘要反映最后真实opener对应渠道，而非跳过／仅Pick的渠道；每次尝试单独保留Kind、提交、FirstByteMs和耗时，FirstByteMs不加连接时间。

## 8. 横切约定（细则在 01-工程规范）

### 8.1 RequestID

入口中间件生成（`req_` + ULID），写入响应头 `X-Request-Id`；注入 context，贯穿日志 / trace / usage_records。

### 8.2 错误响应体与错误码

OpenAI 风格 + request_id：

```json
{ "error": { "message": "...", "type": "gaigate_error", "code": "gaigate_quota_exceeded" },
  "request_id": "req_01J..." }
```

网关自身错误码统一前缀 `gaigate_`。B3 冻结口径：响应未提交时，已取得的上游 400／404／422 合法 OpenAI 错误对象保留其 error 内容并补顶层 request_id；上游 401／403 改为 502 `gaigate_upstream_auth_failed`，上游 429／5xx／网络或协议错误改为 502 `gaigate_upstream_error`，网关超时改为 502 `gaigate_upstream_timeout`。其他上游状态归 502；不盲透传敏感错误体、任意响应头或凭据。完整映射及脱敏边界见 13.3。响应已提交时不追加 JSON／错误 SSE／伪造 Done，由最外层 HTTP handler 异常中止响应。

### 8.3 日志

结构化 JSON（slog），字段：`ts, level, msg, request_id, user_id, channel_id, model, latency_ms, status_class`。细则在 01。
