## 1. 本文档的作用与冲突处理

- 设计文档是"为什么"层，本文档是"执行事实"层。两者冲突时：**执行以 00 为准**；如冲突暴露了设计缺陷，先在 §11 变更记录中修正 00，再动代码。
- 本文档的直接受众是**每一份 L2 施工文档背后的独立 vibecoding 会话**。因此所有跨模块共享的事实（接口签名、表结构、Redis key、编号、批次）必须且只能在这里唯一定义。
- 契约（§6、§7）的修改权限在"00 变更流程"（§10），任何 L2 会话无权自行变更契约。

## 3. 系统概览

### 3.1 数据面管道（一条请求的生命周期）

```
客户端
  │ POST /v1/chat/completions   (Authorization: Bearer sk-...)
  ▼
[10 骨架]      RequestID 注入 → 访问日志 → recover
  ▼
[13 access]    ① 鉴权：Key → Principal（用户/Key/分组）
  ▼
[17 meter]     ② 配额预检：硬阈值拒单，软阈值打告警点
  ▼
[16 router]    ③ 路由：模型(别名)→候选渠道链（过滤禁用/熔断）
               ④ 容灾执行：逐个尝试，首字节失败 → 下一候选
  ▼
[15 proxy]     ⑤ 流式转发：背压/取消传播/双超时，逐分片累计 token
  ▼
[17 meter]     ⑥ 结算：用量落账（usage_records）+ 配额计数
  ▼
[18 metrics]   全程打点：延迟/错误/成本，按渠道/模型/用户维度
```

横切支撑：`[11 store]` MySQL 冷数据 + Redis 热状态；`[12 mock]` 可编程上游；`[14 channel]` 渠道健康与端点选择；`[19 web]` 管理与用户页面；`[20 deploy]` 部署与观测面板。

### 3.2 全局时序约束（三句话，凌驾于所有 L2 之上）

1. **容灾只发生在首字节之前**。响应头一旦写给客户端，该请求不可再切换上游；流式中断视为该渠道一次失败，计入健康与熔断统计。
2. **配额是两阶段语义**：预检放行 → 消费后结算。预检不阻塞请求路径；竞态的具体机制（弹性阈值 / 预扣回补 / 事后核销）由 17.2 冻结，但语义不可变。
3. **一个 RequestID 贯穿始终**：日志、指标、账单三者必须能凭同一 RequestID 对账。

## 5. 依赖规则

### 5.1 分层（依赖只能自上而下）

```
第 0 层 基座       11 store、12 mock-provider、共享内核 internal/provider
第 1 层 数据面     13 access、14 channel、15 proxy、16 router、17 meter
第 2 层 观测视图   18 metrics（横切，被第 1 层依赖）、19 web
第 3 层 部署       20 deploy
装配层            10 骨架（依赖全部，组装；无人依赖它）
```

禁止：反向依赖、跨层环、同层模块间非契约依赖。

### 5.2 依赖边（模块级）

```
internal/provider（共享内核：接口 + 统一请求/响应类型，不 import 任何业务包）
    ▲ 实现：13 的 openai 适配器
12 mock-provider → 独立 HTTP 上游，不实现 Provider；internal/mock 不依赖其他 internal 包，cmd 仅装配自身模块；13 的适配器经 HTTP 调用
13 access   → 11 store（用户/Key 读取）、内核
internal/provider/openai → internal/provider（13.2 的适配器子包；标准库 HTTP，不 import access）
14 channel  → 11 store（渠道/Key 表）、内核（产出 provider.Endpoint）
16 router   → 14 channel（健康判定 IsAvailable、端点选择 EndpointPicker）
             11 store（别名/渠道列表）、15 proxy（执行器调用转发）、17 meter（结算）
15 proxy    → 内核（消费 Provider 流）
17 meter    → 11 store（配额/账单表）
18 metrics  → 无业务依赖（被 13~17 打点调用）
19 web      → 13（Key 服务／身份接缝）、14/17 暴露的管理与读取 API、11 store
20 deploy   → 全部（打包与编排）
```

关键说明：

- **健康与熔断是两套独立判定**，同一请求结果分别喂给两者：`14.3 健康状态机`（连续失败/探活信号 → 渠道禁用/恢复，带冷却防抖）与 `16.3 熔断器`（滑动窗口错误率 → 三态开关）。窗口、语义、恢复条件各自独立冻结，不许合并。
- `internal/provider` 是唯一允许被多模块 import 的"类型包"，只放接口与数据类型，禁止逻辑。
- B3 的临时编排和渠道读取放在 `internal/bootstrap`，只由 cmd 装配层调用；它可依赖 access／store／secret／provider／proxy，业务模块不得反向 import bootstrap。access 只消费自身定义的入口接口，不 import router／meter／proxy／bootstrap；B5／B6 在装配处换入正式实现，避免 router 依赖 access 后形成环。
- `internal/middleware` 是既有横切设施，13／16 及装配层可调用其 context／日志辅助；middleware 不反向依赖业务包。13.3 的冻结增量在 AccessLog 入口建立请求内共享摘要，既有 WithUserID／WithModel／WithChannelID 保持签名并同步摘要，使内层派生 context 的字段在外层完成日志中可见；摘要必须请求隔离且并发安全，不存身份凭据或正文。Principal 仍为标准 context 中的身份值，不拿日志摘要授权。

## 6. 接口契约总表（权威，已冻结）

> 签名为 Go。实现包名见 §5.2。此处只冻结**跨模块**契约；模块内部接口由各 L1 冻结。字段级细节（struct 完整字段）在标注的 L2 冻结，此处冻结方法签名与语义。

### 6.1 共享内核 `internal/provider`（13.2 冻结字段）

```go
// Endpoint：一次上游调用的目标，由 14-channel 产出（渠道 + 轮询选出的 Key + 模型名映射）
type Endpoint struct {
    ChannelID int64
    Provider  string // "openai" | "mock" | ...
    BaseURL   string
    APIKey    string // 已解密
    Model     string // 映射后的上游模型名
}

type Usage struct{ InputTokens, OutputTokens int64 }

type ChatRequest struct{ /* OpenAI chat 请求的内部子集，字段清单 13.2 冻结 */ }
type ChatResponse struct{ /* 同上 */ }

type StreamEventKind uint8 // Chunk | UsageDone | Done | Error；符号名见 13.2

type StreamEvent struct {
    Kind  StreamEventKind
    Raw   []byte // 原始 SSE data
    Usage *Usage // 仅 UsageDone 携带
    Err   error  // 仅 Error 携带，必须非 nil；不序列化给客户端
}

type Stream interface {
    Events() <-chan StreamEvent
    Close() error // 幂等：取消上游、关闭 body、等待所属 worker 退出
}

type Provider interface {
    Name() string
    // 非流式。返回响应与用量。
    Chat(ctx context.Context, ep *Endpoint, req *ChatRequest) (*ChatResponse, *Usage, error)
    // 流式。内部错误经由 Error 事件传递；网络层错误由返回值传递。
    ChatStream(ctx context.Context, ep *Endpoint, req *ChatRequest) (Stream, error)
}
```

冻结补充：`Done` 独立表示上游 `[DONE]`，必须向下游转发一次；关闭事件 channel 本身不代表成功。未见 Done 的 EOF／非法帧／读失败均为异常；取消由请求 context 分类，不伪造 Done。Raw 保留 SSE data 负载的内容，非整段 HTTP 字节；组帧规则见 13.2／15.1。`Error.Err` 保留可分类原因。正常流可以缺 usage，不能缺 Done。

### 6.2 access（13）

```go
type Principal struct {
    UserID, APIKeyID, GroupID int64
    Username, Role            string
}

type Authenticator interface {
    // Key 无效/吊销/过期返回可分类错误（映射 401/403，错误码见 §8.2）
```

### 6.5 router（16）

```go
type Plan struct {

type Router interface {
```

### 6.6 meter（17）

```go
type QuotaGuard interface {
    // 硬阈值超限返回 ErrQuotaExceeded；软阈值仅打告警点不拒绝
    Precheck(ctx context.Context, p *access.Principal) error
    // 消费后结算：更新配额已用计数（token 与成本）
    Settle(ctx context.Context, p *access.Principal, u provider.Usage, cost int64) error
}

type UsageSink interface {
    // 异步落账 usage_records（含 request_id）：入队即返回，永不阻塞、无错误返回——
    // 队列满 / 批量重试耗尽由 store 层（11.3 UsageRepo）丢弃并触发 OnDrop
    // （18.1 挂 gaigate_usage_drop_total）；重试在 store worker 内部完成，无独立重试队列。
    // 17.1 的 UsageSink 是 store.UsageRepo 的薄包装，不重复实现队列（台账 #17）
    Record(rec UsageRecord)
}
```

> meter 内部可提供把 QuotaGuard + UsageSink 合并的 façade，属模块内部设计，非契约。

### 6.7 跨模块错误（内核或各包定义，码值段见 §8.2）

`ErrUnauthorized`、`ErrKeyRevoked`、`ErrQuotaExceeded`、`ErrNoCandidate`、`ErrUpstreamUnavailable`、`ErrStreamInterrupted`、`ErrNoPrice`（11.2 引入：模型无生效价格，17.3 决定降级策略）、`ErrNotFound`（11.2 引入：通用不存在，14.1 映射 404）。

B3 冻结补登 `access.ErrKeyExpired`／`access.ErrUserDisabled`，分别映射 403；与既有 `access.ErrUnauthorized`／`access.ErrKeyRevoked` 同属 13.1。13.3 补 `access.ErrModelNotFound` 对应入口 404；13.2 在 core 定义 `provider.ErrStreamInterrupted`／`provider.ErrNoCandidate`／`provider.ErrUpstreamUnavailable`，供后续模块复用而不重复定义。`provider.UpstreamError` 是携带状态、受限错误体及底层原因的可分类类型，支持 errors.As／Unwrap，不以字符串匹配；13.3 的 `access.ExecutionError` 只携带 Cause／WroteHeader／TimedOut，供装配层传回提交与预算状态，不迫使 access import proxy。store 故障保留原因并映射 500，不冒充用户 Key 无效。错误类型的 Error／Unwrap 等薄方法允许在 core，禁止的是业务逻辑。

### 6.8 mock 测试协议（12，v0.8 已冻结）

- 12 是独立的 OpenAI 兼容 HTTP 测试服务，不实现 `provider.Provider`；业务模块经真实 HTTP 链路调用，不 import `internal/mock`。场景名固定为 `normal / slow / downtime / rate_limited / interrupted`，默认及参数细节由 12.1 §3 定义，控制 API 与脚本接口由 12.2 §3 定义。
- 场景优先级：单请求 `X-Mock-Scenario` 覆盖 > 按上游测试 Key 存储的配置 > 全局默认 normal。请求开始时获取一次配置快照；控制更新返回后开始解析的新请求必须读到新值，在途请求沿用旧快照。未知覆盖值拒绝，不静默回落。
- 完成流由 N 个内容帧、可选的 1 个 usage 帧、1 个 `[DONE]` 结束标记组成。三者分别计数；usage 帧 `choices=[]`，仅 `stream_options.include_usage=true` 时发送。失败中断不得伪装为自然完成，不发送 usage 或 `[DONE]`。
- `downtime/refuse` 是接受连接后的无 HTTP 响应断连；不关闭共享 listener，不承诺操作系统特定的连接重置错误。`interrupted` 是已发送指定内容帧后异常终止 HTTP 响应。12.1 必须以真实 TCP/HTTP 客户端验证，不能只用 ResponseRecorder 或 handler 正常返回冒充断流。
- 12-L1、12.1、12.2 与本文 v0.8 修订已于 2026-10-20 经用户确认 review 完成并冻结；下游 13.2／15／14／16 施工前消费本冻结版本。冻结不代表实现完成，12.1 与 12.2 仍逐份施工、独立审查及验收。

### 6.9 B3 转发与装配补充契约（v0.9 已冻结）

1. **单次尝试预算**：proxy 在调用上游 opener 之前启动 TTFB／Overall 计时，覆盖建连、等待响应头和首个可转发结果。opener 接收 proxy 派生的请求 context；禁止先 ChatStream 成功再开始计时。流式 TTFB 在首个合法 data 事件可交给下游时停止；非流式在完整合法 JSON 可交给下游时停止。FirstByteMs 记录这个应用层观测时刻，不宣称 TCP 首字节或客户端收到时间。Overall 持续到写出及资源清理，包含客户端慢写；具体机制见 15.2。
2. **提交边界**：只以实际写出状态 WroteHeader 判定能否另写错误／尝试其他候选；结果类别不能推断提交状态。Write／短写／Flush 失败必须停止后续输出。阻塞写需可被取消／预算打断；仅 select context 不能保证正在 Write 的 goroutine 退出。Gin／包装器不得吞底层 Flush 错误或写 deadline 能力。
3. **错误终止责任**：proxy 返回结果与错误，关闭上游；入口 handler 在已提交且失败时用 http.ErrAbortHandler 异常终止。13.3 同步补齐网关 Recover 对该哨兵的透传及普通 panic 在已提交时的中止路径；不得在已有 SSE 后追加 500 或将截断伪装为正常 HTTP 结束。同时补齐 §5.2 请求摘要，使渠道字段可从内层派生 context 回传外层日志；10.2 的旧验收历史保留，新增实现／回归归 13.3。
4. **入口适配缝**：access 自有 ChatExecutor 仅接收 Principal、ChatRequest 和 ResponseWriter，内部封装正式路由与执行；它不冒充 00 §6.5 接收 Plan 的 router.Executor。B3 的实现由 internal/bootstrap 提供；B5 的装配适配器先 Route 再调用 router.Executor，access 不反向依赖 router。预检缝只含 §6.6 Precheck。
5. **M0 的诚实范围**：仅选择模型已配置渠道中 priority 降序／id 升序的第一个，选该渠道第一把启用 Key；复用 secret 解密和 channel_models 的 upstream_model，不实现权重、健康、熔断、回退或配额。13.3 必须先确认模型别名存在，未知别名 404；/v1/models 返回 OpenAI list envelope，列全部已配置别名，不虚构表内不存在的 enabled 字段。
6. **用户 Key 首次创建**：13.4 提供本地 cmd/g-aigate-key 命令，显式指定用户名并创建 Key；不改 seed、不自动签发固定 Key、不开放任意指定用户的 HTTP 鉴权桩。B3 用户 Key HTTP API 用既有 Bearer 身份限定本人；19.1 再注入登录会话身份。完整 Key 仅在创建成功响应／创建命令的受控标准输出返回一次，其他响应与日志不回显。
7. **包装器前置能力（2026-10-21 主会话裁定，已获用户确认并随 15.1 交付）**：为完成 15.1 已冻结的真实 WrapWriter 正向／错误 Flush 验收，将标准 `Unwrap() http.ResponseWriter` 的最小透明透传及对应行为回归从 13.3 前移至 **15.1 M2**。只允许在 `internal/middleware/wrapwriter.go` 的既有私有包装类型增加该能力，返回直接被包装的下一层 writer；`WrapWriter` 函数签名保持不变，正文仍经原外层／Gin 写入。相关 middleware 测试和 proxy 组合测试纳入 15.1 的完整审查范围，不新增包装框架、业务接口或生产依赖边。不得借此提前修改 Recover／AccessLog／请求摘要、实现双超时／deadline 策略或网关装配；15.2 和 13.3 的其余职责不变。原有不支持能力时的提交前安全拒绝必须保留，真实 WrapWriter 的正向验收不能后置或降低。用户转交并确认 M2 的记录见 15.1 §11.7，独立审查与交付见 §11.12～§11.13；原待确认历史保留于本文 §11，不另设重复开工批准。

8. **Overall写超时归因（2026-10-21 主会话裁定，待用户转交确认）**：允许proxy同步锁存已按15.2 §3.4确定的Overall原因，防止本次写期限超时引发的net/http请求取消把结果改写为ClientCanceled。父先确认仍优先；底层写期限先于预算回调唤醒时，只能以本次Overall有效期限、实际输出超时及无先前独立父原因等证据补判。普通Canceled与该写超时无法分辨先后时按该节统一归Overall，不声称还原物理顺序；其余同时满足情形仍按父、Overall、TTFB顺序。保留实际父／输出／清理原因链，不修改Provider／middleware或公开接口；本补充由15.2实现和独立验收，后续消费者不按错误链含Canceled反推Kind。

## 8. 横切约定（细则在 01-工程规范）

### 8.1 RequestID

入口中间件生成（`req_` + ULID），写入响应头 `X-Request-Id`；注入 context，贯穿日志 / trace / usage_records。

### 8.2 错误响应体与错误码

OpenAI 风格 + request_id：

```json
{ "error": { "message": "...", "type": "gaigate_error", "code": "gaigate_quota_exceeded" },
  "request_id": "req_01J..." }
```

网关自身错误码统一前缀 `gaigate_`。B3 冻结口径：响应未提交时，已取得的上游 400／404／422 合法 OpenAI 错误对象保留其 error 内容并补顶层 request_id；上游 401／403 改为 502 `gaigate_upstream_auth_failed`，上游 429／5xx／网络或协议错误改为 502 `gaigate_upstream_error`，网关超时改为 502 `gaigate_upstream_timeout`。其他上游状态归 502；不盲透传敏感错误体、任意响应头或凭据。完整映射及脱敏边界见 13.3。响应已提交时不追加 JSON／错误 SSE／伪造 Done，由最外层 HTTP handler 异常中止响应。

### 8.3 日志

结构化 JSON（slog），字段：`ts, level, msg, request_id, user_id, channel_id, model, latency_ms, status_class`。细则在 01。
