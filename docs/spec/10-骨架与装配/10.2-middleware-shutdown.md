# 10.2 中间件管道与优雅关闭（L2）

## 1. 模块定位

管道 §3.1 的第 0 环：RequestID 注入 → recover → 访问日志；`/healthz` `/readyz` 探针；优雅关闭全流程。所有业务路由都挂在这条中间件链之下。

## 2. 目标 / 非目标

**目标**：三个中间件 + 探活注册器 + shutdown 流程 + `ResponseWriter` 包装器（保 Flusher）；中间件顺序有测试锁定。

**非目标**：CORS（内部系统不需要）；业务鉴权（13.1）；任何渠道/模型/计量逻辑。

## 3. 输入输出

```go
// internal/skeleton（或 internal/middleware，实现时定名并在本 PR 冻结）
func RequestID() gin.HandlerFunc   // req_+ULID；ctx 注入 + 响应头 X-Request-Id 回显
func Recover() gin.HandlerFunc     // panic → 500 {"error":{...,"code":"gaigate_internal"},"request_id":...} + 堆栈日志
func AccessLog(logger *slog.Logger) gin.HandlerFunc // 请求完成一行摘要（见下）

// 探活注册器：依赖就绪后动态注册（B2 末由 main 注册 MySQL/Redis 检查）
type Probes struct{ ... }
func (p *Probes) Register(name string, check func(ctx context.Context) error)
func (p *Probes) ReadyHandler() gin.HandlerFunc // 全部通过 → 200；任一失败 → 503 + 失败项列表

// ResponseWriter 包装器：透传 http.Flusher 与 http.Hijacker（15 流式依赖，10-L1 风险①）
func WrapWriter(w gin.ResponseWriter) gin.ResponseWriter

// 优雅关闭（main 中实现）：
// SIGTERM/SIGINT → http.Server.Shutdown(ctx=ShutdownTimeout) → 逆序 Close 依赖（meter 落账 → redis → mysql）
```

**中间件顺序（契约，改变须走 00 §10；2026-10-10 实现反馈修正）**：`RequestID → AccessLog → Recover → 路由`。AccessLog 必须在 Recover **之外**（先注册）：panic 展栈时内层 defer 先执行——Recover 先接住 panic 并写出 500，AccessLog 的 defer 后执行，`status_code` 记录真实值；request_id 由最外层 RequestID 保证。原顺序 `RequestID → Recover → AccessLog` 会使 AccessLog 在 500 写出前记录（恒为 200），属文档 bug，由 10.2 实现反馈发现。已知取舍：AccessLog / RequestID 自身 panic 不受 Recover 保护（自有薄代码，风险接受）。

**request_done 日志字段**（00 §8.3 全集）：`ts, level, msg="request_done", request_id, user_id, channel_id, model, latency_ms, status_class, status_code, method, path`（业务字段由后续模块通过 ctx 补充，B2 阶段可为空值占位）。

## 4. 设计说明

1. **readyz 动态注册而非硬编码**：B2 末 store 就绪后注册 MySQL/Redis 检查；B3+ 的模块（如探活任务）可继续追加。滚动更新时 `/readyz` 翻转先于 SIGTERM 生效，这是 K8s 优雅发布叙事的一半。
2. **关闭顺序**：先停止收新请求（Shutdown 等待在途流式 ≤ 60s），再逆序关依赖——落账队列（11.3）必须先 drain 再关 DB，否则丢账。
3. **WrapWriter 是 15-L1 风险①的前置解**：Gin 自身的 ResponseWriter 已实现 Flusher，但自定义中间件再包一层会丢接口——集中提供一个永远透传的包装器，避免每个中间件各自处理。

## 5. 验收标准（可执行）

```bash
go test ./internal/middleware/...    # 用例：① request_id 在日志与响应头一致；② panic 路由返回 500 + gaigate_internal；③ 顺序测试（AccessLog 输出必含 request_id；panic 请求的 request_done 记录 status_code=500）；④ WrapWriter 断言 Flusher/Hijacker 透传；⑤ readyz：注册 1 个失败检查 → 503 且列出失败项
# 优雅关闭验证（分三层；2026-10-10 实现反馈修正：Windows 无法向原生进程发送 SIGTERM，Git Bash kill 是硬终止）：
# 层1（自动化，本 PR）：关闭序列封装为可测函数（http.Server.Shutdown + 逆序 closer），
#     集成测试直接调用该函数：起 server + 挂起在途慢请求 → 触发 → 断言在途完成后退出、
#     closer 逆序执行、超时截断路径（ShutdownTimeout 调成极短值触发）；
#     signal.Notify → handler 的接线仅数行，不做 OS 级测试
# 层2（手动，Windows 可行）：控制台前台运行，Ctrl+C 触发 os.Interrupt → 同一 handler
#     → 日志显示 shutdown 开始、在途 drain 完成、退出码 0
# 层3（真 SIGTERM，挂起到 20.1）：容器内 linux 环境，docker compose stop 发送 SIGTERM，
#     该路径的真实验证在 B8 部署验收完成
# 信号注册契约：os.Interrupt 与 syscall.SIGTERM 同时注册，路由到同一 shutdown 函数
```

## 6. 依赖

上游：10.1（Config）。被依赖：13.3（业务路由挂在本管道下）、15（Flusher/Hijacker）、B2 末的 main 装配（注册探针与关闭序列）。

## 7. 主要风险

- Windows 下无法向原生进程发送 SIGTERM（Git Bash 的 kill 对非 MSYS 进程是 TerminateProcess 硬终止）——已按 §5 分层验证处置：自动化测关闭函数、手动 Ctrl+C 验证 Interrupt 路径、SIGTERM 真实验证挂起至 20.1（容器内）。
- Shutdown 等待期间新连接行为（立即拒绝）需要用例覆盖，避免误判为 bug。
