## 1. 模块边界

**做什么**：独立进程（`cmd/mockprovider`），模拟一个 OpenAI 兼容上游：暴露 `POST /v1/chat/completions`（流式与非流式），行为可编程切换五种场景；提供场景控制 API。

**不做什么**：不做真实推理（返回模板文本）；**不是** `provider.Provider` 的实现——它是 HTTP 服务器，被网关的 OpenAI 适配器（13.2）当作真实上游调用，这样才能真实测试超时、取消、SSE 解析等 HTTP 层行为。

## 2. 场景协议（契约级，14/16 的验收脚本直接引用）

**区分渠道**：mock 用不同的上游 API Key 区分不同"渠道"，每个 key 独立持有场景状态（贴合真实模型：一渠道一账号）。

**控制方式**（优先级从高到低）：

1. 请求头 `X-Mock-Scenario: <name>`——单请求级覆盖，供脚本精确控制；
2. 控制接口 `PUT /admin/scenario`，body `{"key":"sk-mock-a","scenario":"downtime"}`——持续生效，直到再次切换。

**场景定义**（参数可配，默认值在 12.1 冻结）：

| 场景 | 行为 |
|---|---|
| `normal` | SSE 流式返回 N 个 chunk（可配数量/间隔），末 chunk 携带 usage；非流式返回完整响应 |
| `slow` | TTFB 延迟 D 后按 `normal` 继续 |
| `downtime` | 返回 503（或直接拒绝连接，可配） |
| `rate_limited` | 返回 429 + `Retry-After` |
| `interrupted` | 发送 k 个 chunk 后关闭连接（模拟半路断流） |

## 3. 关键设计决策

1. **独立进程而非进程内库**：容灾、双超时、取消传播的测试必须穿过真实 HTTP 栈才有含金量。
2. **按上游 Key 隔离场景**：与渠道模型同构，"渠道 A 挂了、渠道 B 正常"的容灾场景可以精确编排。
3. **场景切换立即生效**（mutex 保护），验收脚本无需等待。

## 4. L2 清单（00 预排 1~2 份，裁定为 2 份）

- **12.1 场景引擎与 OpenAI 兼容端点**：场景状态机、SSE 生成、非流式路径。
- **12.2 场景控制 API 与验收脚本**：`/admin/scenario`、五场景 curl 脚本（入库 `test/e2e/mock_scenarios.sh`，供 B4/B5 复用）。
- 调整理由：单 L2 需同时覆盖服务端点与控制面，拆开后各自可单会话完成，且脚本资产独立沉淀。

## 5. 主要风险

- SSE 断流时机精度：flush 后立即 close 连接即为真实断流，够用；不追求字节级精确。

## 6. 验收要点

B2 检查点贡献：五场景各有一条 curl 断言（状态码 / chunk 数 / 连接中断），`test/e2e/mock_scenarios.sh` 全绿。
