> 状态：已实现（2026-10-17，验收见 §9） | 上游：[11-L1](../11-store.md) | 批次：B2 | 预计工作量：1 天

## 1. 模块定位

账务数据的读写层：usage_records（只追加）、quotas（配置）、bills（物化聚合）。核心特点是**写入异步化**——请求路径上的 Record 永不阻塞、永不失败返回。

## 2. 目标 / 非目标

**目标**：`UsageRepo`（异步队列 + 批量落库 + drain 语义）；`QuotaRepo`（配额配置 CRUD）；`BillRepo`（月账单 upsert 与查询）。

**非目标**：配额的预检/结算语义（17.2，本层只存配置）；计价（17.3）；查询聚合 API（17.3）。

## 3. 输入输出

```go
type UsageRecord struct { // 复用 internal/store/models.go（11.1 §9.7 冻结的列映射，台账 #15）
    RequestID string; UserID, APIKeyID, ChannelID uint64
    Model string; InputTokens, OutputTokens uint32
    Cost int64; LatencyMS uint32; Status string; Estimated int8 /* 0/1 */; CreatedAt time.Time
}

type UsageRepo interface {
    // 永不阻塞、永不返回业务错误：入队即返回。
    // 队列满 → 丢弃并调用 OnDrop 回调（默认 error 日志；B7 由 18 挂 gaigate_usage_drop_total）
    Record(rec UsageRecord)
    SetOnDrop(fn func(rec UsageRecord))
    Close(ctx context.Context) error // drain：把队列中记录全部落库后退出（10.2 关闭序列第一步）
}
// 内部：缓冲 chan（容量 MeterConfig.SettleQueueSize，默认 1024）
//       worker 每 100 条或 500ms 批量 INSERT（事务），失败重试 3 次后放弃 + OnDrop

type QuotaRepo interface {
    Get(ctx, targetType string, targetID int64, period string) (*Quota, error)
    Upsert(ctx, q *Quota) error
    ListByTarget(ctx, targetType string, targetID int64) ([]Quota, error)
}
type BillRepo interface {
    UpsertMonth(ctx, userID, groupID int64, period string, totalCost, tokenTotal int64) error
    List(ctx, filter BillFilter) ([]Bill, error) // 按 user/group/period 过滤
}
```

**UsageRecord 只追加**：不提供 Update/Delete（11-L1 决策②，账目不可变）。

## 4. 设计说明

1. **丢弃可观测而非假装不丢**：队列满是真实会发生的事（DB 抖动 + 流量高峰），丢弃并打点是诚实的工程答案；修复路径（本地 WAL）已在 11-L1 文档化为后置项。面试题："你的计费会丢数据吗？"——标准答案是说出窗口、量化手段（gaigate_usage_drop_total）、修复方向。
2. **批量写入的触发条件**：条数或时间先到者触发——低流量时 500ms 保证及时性，高流量时 100 条摊薄开销。
3. **Close 的 drain 语义**是优雅关闭链路的一环（10.2 §3.2）：先 drain 落账队列，再关 DB 连接，顺序反了就丢账。

## 5. 验收标准（可执行）

```bash
go test ./internal/store/... -run 'TestUsage|TestQuota|TestBill'
# 用例清单：
# ① Record 1000 条 → Close 后 SELECT COUNT(*) == 1000
# ② 队列灌满（容量 1024，灌 5000 条瞬间）→ 丢弃数 + OnDrop 回调数 一致，进程不死锁
# ③ worker 批量：注入慢 DB（事务 hook 人为延迟）→ 观察批量行为（单测用 hook 断言批次大小）
# ④ Close 期间继续 Record → 全部落库（drain 边界）
# ⑤ Quota Upsert 幂等（同 target+period 更新不重复）
# ⑥ Bill UpsertMonth 重复调用取最后值（UNIQUE 键冲突转 update）
```

## 7. 主要风险

- OnDrop 回调在 18 之前只有日志——可接受，B7 接管打点。
- 批量 INSERT 的 max_allowed_sql 长度：100 条 × 记录宽度远低于默认限制，不构成风险，文档留痕。
- 落账批量重试无幂等键（评审建议2 / 台账 #18）：`usage_records.request_id` 为非唯一索引（11.1 DDL），若事务实际提交成功但客户端因 `settleInsertTimeout=5s` 收到超时错误，重试会重复插入同批明细，违背"账单 = 明细求和"单一数据源口径——低概率窗口（§3 强制重试的固有理论风险），修复方向为幂等键/去重，留后续实现轮。

**实现记录（与本文档的对应与补充说明）**：

1. **`UsageRecord` 结构体复用 11.1 模型**：§3 的 Go 片段字段类型（`UserID/APIKeyID/ChannelID int64`、`Estimated bool`、`LatencyMs`）与 11.1 §9.7 冻结的列映射（BIGINT UNSIGNED→`uint64`、TINYINT→`int8`、INT UNSIGNED→`uint32`）不一致；`internal/store` 同包不能重复定义，且 11.1 为已合并交付物，故**复用 `models.go` 的 `store.UsageRecord`**——"与表一一对应"以 11.1 §9.7 为准（01 §9.2 旁证处置；§3 的 Go 片段已于后续文档治理 commit `db88621` 对齐 models.go 类型，本记录保留实现时点的口径）。消费方 17 按 models.go 字段构造（`Estimated` 用 `int8` 0/1，非 bool）。移交见台账 #15。
2. **队列容量**：`NewUsageRepo(db, queueSize)`；`queueSize<=0` 回退 `defaultSettleQueueSize=1024`（`MeterConfig.SettleQueueSize` 默认 1024，10.1 配置层已 fail-fast 校验 >0，此处为直接调用的兜底）。
3. **批量触发与写入**：满 `settleBatchSize=100` 条或 `settleFlushInterval=500ms` 先到者触发（§3/§4 决策②）；批量 INSERT 在事务内（`db.Transaction`）。单次写入带 `settleInsertTimeout=5s` 超时——防 DB 卡死无限拖住 drain（对 §3 的健壮性补充）。
4. **重试口径**：§3 "失败重试 3 次后放弃" 实现为**首次失败后最多重试 `settleBatchMaxRetries=3` 次（共 4 次尝试）**；耗尽后逐条走 OnDrop。
5. **OnDrop 与丢弃可观测**：默认 `slog.Error("usage_record_dropped", request_id/user_id/channel_id/model)`；`SetOnDrop` 可替换（B7 由 18 接管为 `gaigate_usage_drop_total`）。另维护进程内 `dropped` 计数供用例②与 18 打点。
6. **`Record` 语义**：非阻塞 send（队列满即丢）；入队前维护 `pending`（已入队未落库）计数供 Close 判静默；`CreatedAt` 零值按调用时刻（UTC）补齐；Close 屏障后走丢弃路径。
7. **`Close` drain 语义**：① 等 `pending` 归零（**Close 期间并发 `Record` 的记录也在此窗口落库**——用例④）→ ② 屏障（持写锁置 `done`、关队列，阻断后续入队）→ ③ worker 排空剩余并退出。ctx 超时提前返回错误，但已入队记录仍由 worker 后台排空落库；`sync.Once` 保证幂等。
8. **`QuotaRepo`**：`Upsert` 走 `clause.OnConflict`（唯一键 `uk_quota_target(target_type,target_id,period)`）冲突转 update → 幂等（用例⑤）；`Get` 未命中 `ErrNotFound`；`ListByTarget` 按 `period` 升序。
9. **`BillRepo`**：`UpsertMonth` 走唯一键 `uk_bills_user_period(user_id,period)`，冲突转 update（`group_id/total_cost/token_total`；`created_at` 保留首次物化时间）；`List` 支持 user/group/period 过滤，`period` 降序、同期 `user_id` 升序。新增 `BillFilter` 与 `QuotaTarget*` / `QuotaPeriod*` 常量（域值取自 11.1 §3 DDL 注释）。
10. **`main` 关闭序列接线**：抽出 `buildDeps(mysqlClose, usageDrainClose)`，登记序 `[mysql, usage-repo]` → 逆序关闭时 **drain 先于关 DB**（10.2 §4 决策②兑现点），由 `TestBuildDepsUsageDrainClosesBeforeMySQL` 锁定。10.2 §9.4 "按序追加：drain → redis → mysql" 措辞易被读成"按关闭顺序追加"，实为**逆序注册**；11.4 redis 须注册在 `mysql` 与 `usage-repo` **之间**（非追加末尾），以维持关闭顺序 `drain → redis → mysql`（已在 `buildDeps` 注释登记；移交见台账 #16）。
11. **测试钩子**：`testHookFlush`（批量写入前回调，断言批次大小）/ `testHookDelay`（写入前延迟，模拟慢 DB）仅测试用（生产 nil）；`newUsageRepo`（构造，不启动 worker）与 `start()` 分离，使用例能在启动前注入钩子。
12. **接口归属**：`UsageRepo`/`QuotaRepo`/`BillRepo` 定义在 store 包内（同 11.2 模式）；跨模块 id 参数用 `int64`，内部转 GORM `uint64`（对齐 00 §6.4 惯例）。`usage_records` 只追加——未提供 Update/Delete（11-L1 §3 决策②）。
13. **未涉及的边界**：不做配额预检/结算语义（17.2）、不做计价与聚合 API（17.3）；`QuotaRepo` 只管 MySQL 配置表，Redis 已用计数器是 11.4 的 `QuotaCounter`，本层不碰。
