---

## 1. 模块边界

**做什么**：模型名（别名）→ 候选渠道解析；四种路由策略；三态熔断（Redis Lua 原子滑动窗口）；容灾执行器（顶层编排管道第④~⑥步）。

**不做什么**：健康禁用判定（14.3）；流转发机制（15）；计量语义（17）。执行器只编排，不实现被编排者的逻辑。

## 2. 接口

- 跨模块契约：00 §6.5（`Router` / `Plan` / `Breaker` / `Executor`）。
- 路由策略枚举（别名级可覆盖，全局默认，16.2 冻结配置结构）：
  - `weighted`（默认）：可用候选按渠道权重加权随机；
  - `cost_first`：按 `model_prices` 单价升序；
  - `latency_first`：按 `channels.latency_p99_cache` 升序（粗粒度，首版够用）；
  - `fallback_chain`：严格按别名配置顺序（default → fallback_ids）。
- 熔断参数（默认值，可配，语义在 16.3 冻结）：窗口 60s；最少样本 20；错误率阈值 50%；open 持续 30s 后转 half-open，放行 1 个探测请求。

## 3. 关键设计决策

1. **回退链由管理员配置，用户只指定模型名**。设计文档"用户可显式指定回退链"在本版收窄——OpenAI 协议没有回退字段，自造 header 破坏兼容承诺；用户级自定义回退列为后续扩展。这是范围收窄决策，面试讲得出为什么。
2. **熔断全状态在 Redis，单点真相**：记录（ZADD）+ 窗口裁剪 + 统计 + 状态转移在一个 Lua 脚本内原子完成。多副本共享同一窗口，天然一致——"熔断器放进程内存"在本架构下是错误答案（每副本只见部分流量），这是必考点的标准答案。
3. **half-open 并发控制**：多副本同时到达 half-open，Lua 内 CAS 只放行一个探测请求，其余按 open 处理。
4. **候选处理顺序**：先过滤（禁用 + 熔断）再按策略排序；执行器对每个候选在**尝试时点**再次 `Allow()`（计划与执行之间状态可能变化）。
5. **执行器语义**（16.4 冻结）：逐候选尝试 `ChatStream` → TTFB 前失败（含 TTFB 超时）→ `OnResult + ReportRequestResult` → 下一候选；写出成功后中断 → 计失败、不切换（00 §3.2.1）；每次尝试独立 span 与打点；结束后触发 17 的结算。

## 4. L2 清单（与 00 §4.1 预排一致，无调整）

- **16.1 模型→渠道解析**：别名、默认渠道、回退链展开、候选过滤（禁用/熔断）。
- **16.2 路由策略**：四种策略排序 + 别名级覆盖配置。
- **16.3 三态熔断**：Lua 脚本（窗口统计 + 状态机 + half-open CAS）、参数可配、miniredis 并发测试。
- **16.4 容灾执行器**：候选迭代、切换/不切换边界、结果上报（熔断 + 健康双喂）、结算触发、打点。

## 5. 主要风险

- Lua 脚本正确性是全模块命门——验收必须包含 `-race` 下的并发窗口测试与状态转移全路径表驱动用例。
- `latency_first` 依赖 14 的缓存列，粒度粗——文档化，面试讲"数据来源与局限"。
- 全部候选不可用时返回 503 `gaigate_no_candidate` 并打告警点（18）。

## 6. 验收要点

B5 检查点（全模块，项目最重的一场）：mock 双渠道编排 `normal` + `downtime` → 请求成功且自动落在好渠道；主渠道切 `rate_limited` → 熔断打开 → 切换备渠道 → 客户端无感知 → 主渠道恢复 → 30s 后半开探测成功 → 熔断闭合 → 流量回归。脚本入库 `test/e2e/failover.sh`；`go test -race ./internal/router/...` 全绿。
