## 1. 模块边界

**做什么**：渠道 CRUD 管理 API 与连通性测试；多 Key 加权轮询 + 密钥解密 + 模型名映射（产出 `provider.Endpoint`）；探活定时任务；健康状态机（禁用 / 恢复 / 冷却 / 防抖，`HealthRegistry`）。

**不做什么**：熔断（16.3——那是请求级滑动窗口三态，与本模块的渠道级持续可用性判定是两套独立机制，窗口、阈值、恢复语义均不同，见 00 §5.2）；路由选择（16）。

## 2. 接口

- 跨模块契约：00 §6.4（`HealthRegistry` / `EndpointPicker`）。
- HTTP（admin，鉴权由 19 的会话中间件保护）：`GET/POST/PUT/DELETE /api/v1/admin/channels`、`POST /api/v1/admin/channels/:id/test`（发最小非流式请求，返回延迟与结果）。
- 健康状态机参数（默认值，全部可配，语义在 14.3 冻结）：连续失败阈值 5 → 禁用；禁用冷却 60s；冷却结束后半开——探活成功才恢复；探活周期 30s。

## 3. 关键设计决策

1. **健康与熔断分离**（本模块最重要的可讲点）：健康状态机回答"这个渠道还能不能长期信任"（连续失败/探活信号 → 禁用是**排他性**的，禁用后不进候选）；熔断回答"这个渠道最近一分钟错误率高不高"（比例信号 → 三态，半开可探测恢复）。同一请求结果同时喂给两者（`ReportRequestResult` + `Breaker.OnResult`），但判定独立。
2. **多 Key 平滑加权轮询（SWRR，nginx 同款）**：相比随机加权，SWRR 避免短时间内连续命中同一 Key；单 Key 连续失败时临时降权跳过，恢复后回归。
3. **状态存 Redis**（key 见 00 §7.2 `gaigate:health:{channelID}`）：多副本共享同一份健康真相；`channels` 表的 `error_rate_cache / latency_p99_cache` 仅作展示缓存列异步刷新，**路由判定不读它们**。
4. **探活用真实最小 chat 请求**（max_tokens=1）而非 `/models`：`/models` 不验证 Key 额度与推理路径，探活结果不代表可用性。

## 4. L2 清单（与 00 §4.1 预排一致，无调整）

- **14.1 渠道 CRUD 与连通性测试 API**：管理接口 + 手动测试（调 mock 的 `X-Mock-Scenario` 可直接演示）。
- **14.2 多 Key 加权轮询与端点装配**：SWRR + AES-256-GCM 解密 + `channel_models` 模型名映射 → `provider.Endpoint`。
- **14.3 探活任务与健康状态机**：定时任务、Redis 状态、禁用/冷却/半开恢复语义、防抖。

## 5. 主要风险

- 探活流量成本：每渠道每 30s 一个 1-token 请求，内部规模可忽略；探活失败到禁用生效之间存在窗口，在途请求自然失败并由熔断兜底——两套机制的衔接点，面试必问。
- 解密每请求一次：首版直接解，缓存解密结果（TTL = 渠道配置版本）作为后置优化，先保证正确。

## 6. 验收要点

B4 检查点（全模块）：脚本将 mock 渠道切 `downtime` → 连续 5 次请求失败 → 渠道禁用（`IsAvailable=false`，admin 页可见）→ 冷却期后探活（切回 `normal`）→ 自动恢复。全链脚本入库 `test/e2e/health_lifecycle.sh`。
