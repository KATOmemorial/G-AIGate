## 1. 模块定位

管道第⑤步的机制核心：把 `provider.Stream` 的逐事件写到客户端，分类结果（可否切换）交给上层。**它不知道候选、不知道重试，只知道"这一条流传得怎么样"**。

## 2. 目标 / 非目标

**目标**：`Forwarder`（15-L1 §2 契约的实现）；响应头管理；Flush 时机；`ForwardResult` 五分类；非流式写出 helper。

**非目标**：候选切换（16.4）；背压链完整验证与双超时计时（15.2，本 PR 预留钩子）；计量累计（onChunk 回调透出，17 消费）。

## 3. 输入输出

```go
// internal/proxy —— 本 L2 冻结
type ResultKind string
const (
    ResultSuccess          ResultKind = "success"
    ResultTTFBTimeout      ResultKind = "ttfb_timeout"      // 未写响应头 → 可切换
    ResultStreamInterrupted ResultKind = "stream_interrupted" // 已写头 → 不可切换
    ResultOverallTimeout   ResultKind = "overall_timeout"    // 已写头 → 不可切换
    ResultClientCanceled   ResultKind = "client_canceled"    // 已写头
)

type ForwardResult struct {
    Kind        ResultKind
    WroteHeader bool          // 16.4 切换判定的唯一依据
    FirstByteMs int64
    Chunks      int
    Usage       *provider.Usage // UsageDone 捕获（onChunk 之外冗余返回，17 直接取用）
}

type ForwardOptions struct {
    TTFBTimeout, OverallTimeout time.Duration
    // StreamBuffer 在 13.2 适配器侧生效，此处不重复配置
}

type Forwarder interface {
    Forward(ctx context.Context, w http.ResponseWriter, s provider.Stream,
        opts ForwardOptions, onChunk func(provider.StreamEvent)) (ForwardResult, error)
}

// 非流式：直接写完整 JSON 响应（经 13.2 Chat 返回）
func WriteNonStream(w http.ResponseWriter, resp *provider.ChatResponse) error
```

**转发流程（契约级）**：

```
进入 Forward → 启动 TTFB 计时（15.2 完整化）
→ 等待首个事件：
   Error 事件 / ctx 取消 / 超时 → 未写头，直接返回（TTFBTimeout / ClientCanceled）
   首个 Chunk/UsageDone → 写响应头（见下）→ 写首帧 + Flush
→ 循环：读事件 → onChunk(ev) → 原样写 "data: <Raw>\n\n" + Flush → Chunks++
   UsageDone 帧：照常转发（13.2 决策②）+ 捕获 Usage
   Error 事件 → 返回 StreamInterrupted（已写头）
   ctx 取消（客户端断开）→ s.Close() → 返回 ClientCanceled
   OverallTimeout 到 → s.Close() → 返回 ResultOverallTimeout
→ 流自然结束 → 返回 ResultSuccess
```

**响应头（契约）**：`Content-Type: text/event-stream; charset=utf-8`、`Cache-Control: no-cache`、`X-Accel-Buffering: no`（穿透 nginx 类反代缓冲）；**不设置 Content-Length**（流式无长度）；禁用 gzip。

## 4. 设计说明

1. **`WroteHeader` 是模块间最关键的布尔量**：00 §3.2.1"容灾只发生在首字节之前"在代码里就是这个字段——16.4 只看它决定切换与否。字段虽小，语义在此文档冻结。
2. **原样转发 `Raw`**：网关不解析重组 chunk 内容（除 usage 提取），保证 token 流与上游逐字节一致——这是"透传"的准确含义，也把解析开销降到最低。
3. **onChunk 回调同步调用**：17.1 的计量累计在转发循环内联执行（无额外 goroutine/队列），因为累计是 O(1) 操作，异步化只会引入乱序与丢失窗口。

## 5. 验收标准（可执行）

```bash
go test ./internal/proxy/... -run TestForward   # 用例（httptest + 假 Stream）：
# ① 正常流：N Chunk + UsageDone → ResultSuccess，WroteHeader=true，Chunks=N，
#    Usage 捕获正确，客户端收到 N+1 帧与 [DONE] 语义由 13.2 保证
# ② 首事件前 Error → 未写头，客户端零字节
# ③ 第 k 帧后 Error → StreamInterrupted，客户端已收 k 帧
# ④ 客户端断开（cancel ctx）→ s.Close() 被调用（mock Stream 断言）
# ⑤ onChunk 收到全部事件且顺序与流一致
# ⑥ 响应头三件套 + 无 Content-Length
# ⑦ WriteNonStream：JSON body 与 Content-Type: application/json
```

## 7. 主要风险

- 非 Flush 透传路径（中间件包装丢 Flusher）——10.2 的 WrapWriter 已解，验收用例⑥经包装链跑一遍。
- UsageDone 在 Chunk 之前到达的病态流（上游实现错误）：照常转发并捕获，不特殊处理——网关对上游 bug 保持透明。
