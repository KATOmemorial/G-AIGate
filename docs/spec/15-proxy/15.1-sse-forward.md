## 1. 模块定位

一次上游尝试的转发机制：从注入的 opener 获取 stream／完整 JSON，输出、记录提交状态并返回结果。它不认识候选、用户或配额；不选择渠道和重试。入口 handler 负责错误 HTTP 终止。

## 2. 目标 / 非目标

目标：Forwarder、两种 opener、结果结构、SSE data／Done 重建、usage 捕获、同步回调、Write／短写／Flush 错误停止、非流式直接写出、上游 Close 所有退出路径。

2026-10-21 最小实施归属补充：用户随 M2 确认后，在本 L2 纳入 §3.3 的标准 WrapWriter.Unwrap 透明能力和对应行为回归，兑现已有正向验收；不扩展其他中间件职责。

非目标：预算及阻塞写完整保障（15.2）、容灾（16.4）、计量算法（17）。15.1 不能以假 writer 通过就宣布 15 模块验收。M1 机制与错误路径，M2 流／非流式及上下游接口回归，逐段停点。

## 3. 输入输出

```go
// internal/proxy；生产代码只依赖 provider 类型和标准库
type ResultKind string
const (
    ResultSuccess ResultKind = "success"
    ResultUpstreamError ResultKind = "upstream_error"
    ResultStreamInterrupted ResultKind = "stream_interrupted"
    ResultTTFBTimeout ResultKind = "ttfb_timeout"
    ResultOverallTimeout ResultKind = "overall_timeout"
    ResultClientCanceled ResultKind = "client_canceled"
    ResultWriteError ResultKind = "write_error"
)
type ForwardResult struct {
    Kind ResultKind
    WroteHeader bool
    FirstByteMs int64
    Chunks int
    Usage *provider.Usage
}
type ForwardOptions struct {
    TTFBTimeout, OverallTimeout time.Duration
}
type StreamOpener func(context.Context) (provider.Stream, error)
type ResponseOpener func(context.Context) (*provider.ChatResponse, *provider.Usage, error)
type Forwarder interface {
    Forward(ctx context.Context, w http.ResponseWriter, open StreamOpener,
        opts ForwardOptions, onChunk func(provider.StreamEvent)) (ForwardResult, error)
    ForwardNonStream(ctx context.Context, w http.ResponseWriter, open ResponseOpener,
        opts ForwardOptions) (ForwardResult, error)
}
func NewForwarder() Forwarder
```

原始 ctx 是客户端请求 context。opener 必须使用传入的派生 ctx，不捕获旧 ctx 忽略预算。TTFB／Overall 参数均须正数（与配置校验一致）；错误参数或 nil opener／writer 在调用 opener 和提交前返回普通错误。15.1 接入取消和生命周期，15.2 完成定时器与写 deadline，不更改签名。

FirstByteMs 初始 -1；首个合法可转发 data 就绪时记从方法进入起的毫秒耗时，非流式为完整 JSON 就绪；不是原始 socket 首字节／客户端收到时间。Chunks 只计成功 Write+Flush 的 Chunk，不含 UsageDone／Done，失败帧不计。Usage 取已成功转发的 UsageDone 的副本；重复 usage 帧保留透传，结果取最后一份（正常 mock 仅一份）。

WroteHeader：writer 在调用前应未提交；写 Header map 不算提交。第一次可能触发真实头／正文提交的操作之前保守置 true；即使该 Write／Flush 失败也不得重置。Gin 的 WriteHeader 可能只设置状态，所以实际 Write／Flush 边界与原生 writer 要一起验证。ResultKind 只描述原因，不能替代这个布尔量。

### 3.1 流式状态机

1. 在 opener 前建立派生请求生命周期，成功后唯一 owner 接管 Stream，所有路径最终 Close；nil Stream 属上游协议错误。15.2 在此起点创建预算。
2. 只在首个合法 Chunk／UsageDone／Done 就绪后设置成功响应头并开始写；Error／提前关闭／取消均不提交成功头。Done-only 是合法空流，也输出一次 Done。
3. Chunk／UsageDone 按 Raw 重建 SSE data；Raw 内 LF 拆为多条 data 行，保持重组后的 data 值。逐帧 Write 后 Flush，保持空行分隔。Done 发送 data: [DONE] 加空行，成功后立刻结束，丢弃终止后事件并 Close。
4. 成功转发 Chunk／UsageDone 后同步调用 onChunk（可 nil）；不对 Done／Error 调回调，不启动额外队列。回调只做内存累计，不阻塞网络／SQL，17.1 负责算法；发生失败的帧不计量为已交付。
5. Error 返回 ResultStreamInterrupted 并保留 Err；channel 提前关闭且未见 Done 同样匹配 provider.ErrStreamInterrupted。opener 返回错误为 ResultUpstreamError；ctx／预算原因优先交 15.2 分类。
6. Write 非 nil 错误、短写、底层 Flush 错误立刻停止，不消费／输出后续帧，不补 Done；返回 ResultWriteError 及原因。结果根据当时提交状态填写，上游及时关闭。

响应头：Content-Type: text/event-stream; charset=utf-8、Cache-Control: no-cache、X-Accel-Buffering: no；移除 Content-Length，不启 gzip，不复制任意上游头。proxy 不抢先 Flush 头来“降低 TTFB”。

### 3.2 非流式

ForwardNonStream 调用 ResponseOpener，直接使用 Provider.Chat 的完整 JSON；不通过 SSE 累积。校验非 nil 响应、合法完整 JSON 对象及 Usage 一致后设置 application/json、写原 Body；保留 JSON 内容，不补造 usage。成功 Chunks=0；Usage 是返回值副本。Write／短写／Flush 或取消错误遵守同样提交规则，错误未提交时留给 handler 映射。

### 3.3 WrapWriter 最小透明能力（2026-10-21 主会话裁定，待用户随 M2 确认）

依据 00 §6.9 第7项，将原计划归 13.3 的标准 Unwrap 前置能力和对应回归提前到本 L2 M2，**不后置或降低 §5 的真实包装链正向验收**。

- 唯一生产跨目录增量：在 `internal/middleware/wrapwriter.go` 的既有私有包装类型增加 `Unwrap() http.ResponseWriter`。只返回直接被包装的下一层 writer，不跳过 Gin 或其他中间层；`WrapWriter` 函数签名和其他行为不变。proxy 生产包仍只依赖 provider／标准库，不反向 import middleware。
- 保持正文经原外层 writer 写入，Gin 的 Status／Size／Written 和 AccessLog 必须反映真实写出；Unwrap 提供能力追踪，不授权绕过正文统计或重写 Flush 行为。

## 4. 设计说明

opener 让时间预算包含真正的请求发起；流式与非流式共享一次尝试的生存期。显式 Done 解决旧稿中 parser 吃掉 Done 而 proxy 无法转发的断点。proxy 返回错误不向客户端再写错误体，由 13.3 统一执行未提交 JSON／已提交异常中止策略。

底层 Flush 错误不能被 Gin 的无返回值 Flush 吞掉；要沿实际包装链获取支持错误 Flush 的能力，同时保持 Gin 的状态统计正确。不要直接绕过 Gin 写正文导致 AccessLog 误记未写出。

### 11.3 包装器缺口与主会话裁定项

实际方法集：Gin 1.12.0 的 `*responseWriter` 实现 `Unwrap() http.ResponseWriter`，但 `gin.ResponseWriter` 接口未声明它；`internal/middleware/wrapwriter.go` 的 `wrapWriter` 只嵌入该接口，因此没有 Unwrap／FlushError。Go 1.25 的 ResponseController.Flush 优先调用无返回值 Flusher，直接对 Gin／WrapWriter 调用也无法得到底层 Flush 错误。proxy 因而预先沿可追踪 Unwrap 查找 FlushError，正文保留外层 Write，不做静默 void Flush 降级。

受影响用例是 §5“现有 middleware.WrapWriter 的真实提交统计和底层 Flush 错误”**正向**验证；当前只能证明安全拒绝。§5 的完整验收与 10.2 §10／13.3 §3.3 将包装补齐明确归 13.3 的交付顺序存在待裁定衔接。本会话没有权限自行修改 middleware 或降低 §5 标准。

最小建议提交主会话裁定：保持补齐归 13.3，由主会话明确该正向验收的接续／最终关闭时点；若要求 15.1 完整验收前通过，则由主会话明确最小包装器增量的实施授权与归属，再回归实际链。可追踪 `Unwrap` 是最小方向，不是本轮已获授权的实现；仍需保持 Gin 正文统计并在真实链验证 FlushError／后续 deadline。该问题不妨碍 M1 核心机制自测，**但不能据此宣称完整 15.1 §5 已通过**。
